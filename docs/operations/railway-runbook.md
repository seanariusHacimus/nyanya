# Railway: что нужно сделать руками. Runbook для владельца

Этот файл — про действия в панели Railway и в её командной строке. Всё, что можно было
сделать кодом, уже сделано и лежит в репозитории; всё остальное требует доступа к аккаунту
Railway, денег или решения владельца, поэтому описано здесь по шагам.

**Что уже готово в коде** (ничего в панели для этого включать не нужно):

- `nyanya-app/src/app/api/health/route.ts` — адрес `/api/health`, который отвечает
  `{"status":"ok","db":"ok","ms":N}` со статусом 200, когда приложение живо и видит базу, и
  `{"status":"error","db":"error","ms":N}` со статусом 503, когда база недоступна. Без входа,
  без кэша (`Cache-Control: no-store`), наружу не отдаёт ни текста ошибки, ни адреса базы;
  подробности пишутся в лог сервиса строкой `[health] база недоступна`. Отвечает на GET и
  на HEAD.
- `nyanya-app/railway.json` — `healthcheckPath: "/api/health"`, `healthcheckTimeout: 120`,
  `restartPolicyType: "ON_FAILURE"`, `restartPolicyMaxRetries: 10`.

**Чего в этом файле нет и не будет**: готовых паролей, ключей и чужих счетов. Ни один шаг
отсюда нельзя выполнить «за владельца» — все они меняют боевую систему.

Цены ниже — из документации Railway на **16 сентября 2026**; перед тратой сверьтесь с
`railway.com/pricing`, тарифы меняются. Текущее состояние проекта (регион, тариф, размер тома)
в этом файле не зафиксировано намеренно: у автора файла нет доступа к боевому аккаунту,
поэтому каждый раздел начинается с «посмотрите в панели».

## 0. Порядок работ

Делать сверху вниз, порциями, между ними сайт целый:

| Этап | Что | Простой | Деньги |
|---|---|---|---|
| A | Проверка живости + политика перезапуска (§1) | нет | $0 |
| B | Внешний монитор (§2) | нет | $0 |
| C | Снимки тома: расписание + базовый снимок (§3.1) | нет | центы |
| D | PITR (§3.2) | ~1 мин перезапуска Postgres | центы–$1 |
| E | Ежедневный `pg_dump` в бакет (§3.3) | нет | центы |
| F | Учебное восстановление (§4) | нет | $0 |
| G | Переезд в Амстердам (§5) | **5–15 мин и больше** | $0 |
| H | `railway.json` → `.railway/railway.ts` (§7) | нет | $0 |

Правило владельца, которое действует во всех этапах: **до и после каждого деплоя и до и после
переезда снимаем счётчики базы** и сверяем их.

```sh
# из панели: Postgres → Data, или через railway connect
select (select count(*) from "user")                as users,
       (select count(*) from specialist_profiles)   as profiles,
       (select count(*) from documents)             as documents,
       (select count(*) from reviews)               as reviews,
       (select count(*) from contact_unlocks)       as unlocks,
       (select count(*) from favorites)             as favorites,
       (select count(*) from notifications)         as notifications;
```

`session` меняется сама (люди входят и выходят) — её сверять не нужно.

## 1. Проверка живости: что включить в панели

Railway опрашивает `healthcheckPath` **только в момент деплоя**: пока новый контейнер не
ответит 2xx, трафик остаётся на старом релизе. После переключения платформа этот адрес больше
не трогает — непрерывного мониторинга у Railway нет, он в §2.

Значения уже лежат в `railway.json`, но **продублируйте их в панели** — это не перестраховка,
а подготовка к отсечке 1 декабря 2026 (§7): после неё файл перестанет читаться, и без дубля
тихо исчезнут и проверка живости, и предзапуск миграций.

Сервис `nyanya` → **Settings → Deploy**:

| Поле | Значение |
|---|---|
| Healthcheck Path | `/api/health` |
| Healthcheck Timeout | `120` |
| Restart Policy | `On Failure`, Max Retries `10` |
| Pre-Deploy Command | `npm run db:migrate` |
| Start Command | `npm run start` |

Почему так:

- **120 секунд.** По умолчанию Railway ждёт 300 секунд. Миграции идут в pre-deploy и в этот
  счёт не входят, а `next start` поднимается за секунды — 120 с запасом хватает, зато
  сломанный релиз признаётся сломанным вдвое быстрее. Если когда-нибудь старт станет дольше
  (тяжёлая инициализация), симптом виден в логах деплоя, лечится поднятием числа.
- **On Failure ×10, а не Always.** `Always` недоступен на бесплатном и пробном тарифах; 10
  перезапусков — значение по умолчанию у Railway и работает на любом тарифе. В файле раньше
  стояло 3 — три попытки сгорают за минуту, и дальше сайт лежит без автоматического подъёма.
- Railway ходит на проверку с хоста `healthcheck.railway.app`. Приложение никого по имени
  хоста не фильтрует, но если когда-нибудь появится такой фильтр — этот адрес должен быть
  в списке разрешённых.

**Проверка после деплоя** (без доступа к панели тоже видно):

```sh
curl -si https://www.nyanya.uz/api/health | head -3      # 200 + cache-control: no-store
curl -s  https://www.nyanya.uz/api/health                # {"status":"ok","db":"ok","ms":…}
curl -sI https://www.nyanya.uz/api/health | head -1      # HEAD → 200
```

## 2. Внешний монитор доступности

Без него о падении сайта первыми узнают семьи. Монитор нужен именно внешний: сервис,
который лежит внутри Railway, падает вместе с регионом Railway.

Что завести — два проверяющих:

1. `https://www.nyanya.uz/api/health` — ожидаемый ответ **200**. Ловит и упавшее приложение,
   и живое приложение без базы (503).
2. `https://www.nyanya.uz/` — ожидаемый **200** и наличие слова `nyanya` в теле. Ловит случай,
   когда база жива, а страница отдаёт 500.

Чем: UptimeRobot или Better Stack (у обоих есть бесплатные тарифы с проверкой раз в 5 минут —
условия уточните на их сайтах, здесь они не воспроизводятся, чтобы не устареть), либо шаблон
Uptime Kuma из каталога Railway. Uptime Kuma — отдельный сервис в вашем же аккаунте: платите
за его ресурсы по обычным ставкам ($10 за ГБ оперативной памяти в месяц, то есть контейнер на
256 МБ — около $2,5/мес), и он не увидит аварию, которая положила весь регион.

Настроить нужно:

- интервал 5 минут, таймаут 30 секунд;
- канал оповещения — почта владельца и/или Telegram; **отправьте тестовое оповещение и
  убедитесь, что оно дошло**, иначе монитор бесполезен;
- не считать аварией один неудачный опрос: оповещать после двух подряд.

**Что делать при оповещении**:

1. `curl -s https://www.nyanya.uz/api/health` — что именно сломалось: `db: "error"` значит
   приложение живо, а база нет.
2. Панель Railway → сервис `nyanya` → Deployments: не идёт ли неудачный деплой; Logs: строки
   `[health] база недоступна` и текст ошибки драйвера.
3. Панель → сервис Postgres: жив ли, не упёрся ли том в размер.
4. Если виноват последний деплой — Rollback на предыдущий (образ хранится 72 часа на Hobby,
   120 часов на Pro; после этого только Redeploy со сборкой).

## 3. Резервные копии

Три уровня, и они не заменяют друг друга:

| Уровень | Что спасает | Чего не спасает |
|---|---|---|
| Снимки тома (§3.1) | удалили данные, сломали схему | стирание тома, потерю аккаунта |
| PITR (§3.2) | ошибку в 15:00 между ночными снимками | потерю аккаунта Railway |
| `pg_dump` в бакет (§3.3) | потерю тома целиком | потерю аккаунта Railway |
| Копия вне Railway (§3.4) | потерю аккаунта Railway | — |

В документации Railway прямым текстом: **«Wiping a volume deletes all backups»** и снимки
восстанавливаются только в тот же проект и то же окружение. Поэтому §3.3 и §3.4 не
опциональны, если данные семей и специалистов вам дороги.

### 3.1. Уровень 1: снимки тома

Панель → сервис **Postgres** → вкладка **Backups** → включить расписания:

- **Daily** — раз в 24 часа, хранится 6 дней;
- **Weekly** — раз в 7 дней, хранится 27 дней;
- **Monthly** — раз в 30 дней, хранится 89 дней.

Можно включить все три сразу. То же из командной строки:

```sh
railway link                      # выбрать проект nyanya.uz, окружение production, сервис Postgres
railway postgres pitr schedule set --daily --weekly --monthly
railway postgres pitr schedule list
```

Сразу сделайте базовый снимок и снимите с него срок годности, чтобы он не удалился через
шесть дней:

```sh
railway postgres pitr backup create --name baseline-2026-09
railway postgres pitr backup list                 # взять ID нужного снимка
railway postgres pitr backup lock <ID>            # снять срок истечения
```

**Ограничение**: ручной снимок нельзя сделать, если данные занимают больше половины тома
(«Manual backups are limited to 50% of the volume's total size»). Если упрётесь — сначала
увеличьте том (Live Resize, на Pro делается без простоя).

**Правило на каждый деплой со схемой**: если в коммите есть новый файл в `nyanya-app/drizzle/`,
перед деплоем делаем `railway postgres pitr backup create --name pre-<номер миграции>`.
Миграции у нас только добавляющие и идемпотентные, но снимок стоит центы, а разговор
«а где копия?» — нет.

**Восстановление снимка**: Backups → у нужной даты кнопка **Restore** → Railway готовит
изменение (staged change) → **Deploy**. Новый том встаёт на место старого, **старый остаётся в
проекте отмонтированным** — данные не пропадают. Восстановить можно только в тот же проект и
окружение.

**Сколько стоит**: снимки инкрементальные (copy-on-write), платите только за данные,
уникальные для снимка, по тарифу тома — $0,15 за ГБ в месяц. При базе в сотню мегабайт это
центы в месяц.

### 3.2. Уровень 2: PITR — восстановление на любой момент

Что это даёт: снимок делается раз в сутки, а ошибочный скрипт в 15:00 стирает всё, что
накопилось с ночи. PITR восстанавливает базу на любую секунду внутри окна архива
(примерно 4 недели).

**Перед включением проверьте в панели** (только смотреть, ничего не менять):

- образ сервиса Postgres — `ghcr.io/railwayapp-templates/postgres-ssl:<мажорная версия>`
  (например `:18`). Минорный пин вроде `:18.1` PITR не поддерживает;
- Custom Start Command у сервиса Postgres пуст.

**Включение**: Postgres → Backups → баннер «Point-in-time recovery is off» → **Enable PITR** →
подтвердить. Или `railway postgres pitr enable --service Postgres`. Railway создаст бакет
`Postgres-PITR`, добавит сервису переменные `WAL_ARCHIVE_*` и **перезапустит Postgres** —
это примерно минута недоступности, поэтому делайте ночью по Ташкенту. Через несколько минут:

```sh
railway postgres pitr status --service Postgres   # архиватор здоров, есть первая базовая копия
```

**Восстановление боевую базу не трогает.** Railway поднимает рядом новый сервис
`<имя>-restored-ГГГГММДД-ЧЧММ` с данными на выбранный момент:

```sh
railway postgres pitr restore --service Postgres --at 2026-09-20T22:00:00Z \
  --new-service-name postgres-drill
```

Переключение приложения на восстановленную базу (если однажды понадобится) — ручное: в
переменных сервиса `nyanya` заменить `DATABASE_URL=${{Postgres.DATABASE_URL}}` на ссылку на
новый сервис, сделать redeploy, старый сервис удалить не раньше чем через неделю.

**Сколько стоит**: отдельной платы за PITR нет. Платите за хранение в бакете ($0,015 за ГБ в
месяц) и за исходящий трафик сервиса при загрузке архива ($0,05 за ГБ). Всё сжимается zstd,
у базы с редкой записью это центы; при нынешних объёмах — меньше доллара в месяц.

**Ограничения, о которых нужно помнить**: окно восстановления начинается с первой базовой
копии после включения — «вчера» восстановить нельзя; восстановленная копия архива не ведёт,
для неё PITR включается отдельно.

**Выключение**: Backups → Disable PITR. Railway готовит изменение, которое убирает переменные
и **удаляет бакет с архивом**; если архив хочется сохранить — отредактируйте изменение и
уберите удаление бакета до нажатия Deploy.

### 3.3. Уровень 3: ежедневный `pg_dump` в отдельный бакет

Зачем ещё один уровень: снимки и PITR живут в том же аккаунте Railway и на том же томе.
Дамп `pg_dump` — файл, который можно унести куда угодно и восстановить на любом Postgres.

**Бакет.** Создайте отдельный бакет `nyanya-backups` (New → Bucket) в том же регионе, где стоит
(или будет стоять после §5) сервис Postgres — так дамп не платит за путешествие между
континентами. **Сначала посмотрите в панели, в каком регионе бакет с документами**: у автора
этого файла доступа к боевому аккаунту нет, и проверить это было нечем. **Регион бакета после
создания не меняется** — ошибку придётся исправлять переливкой в новый бакет. Отдельный, а не
общий с документами: у приложения не должно быть ключей к копиям базы.

**Сервис.** New Service → тот же GitHub-репозиторий и ветка `master` → Settings:

| Поле | Значение |
|---|---|
| Service Name | `db-backup` |
| Root Directory | `/nyanya-app/ops/db-backup` |
| Watch Paths | `/nyanya-app/ops/db-backup/**` |
| Cron Schedule | `30 22 * * *` (03:30 по Ташкенту; расписание считается в UTC) |
| Restart Policy | `Never` |
| Public Domain | не выдавать |

Watch Paths обязательны — иначе каждый коммит в приложение будет пересобирать и этот сервис.
Restart Policy `Never` — упавший дамп не должен крутиться в цикле. Новый сервис нельзя
настроить через `railway.json`: Config as Code для новых сервисов закрыт (§7).

**Переменные сервиса `db-backup`** (Variables):

```
DATABASE_URL          = ${{Postgres.DATABASE_URL}}          # внутренний адрес, приватная сеть
AWS_ENDPOINT_URL      = ${{nyanya-backups.ENDPOINT}}
AWS_S3_BUCKET_NAME    = ${{nyanya-backups.BUCKET}}
AWS_ACCESS_KEY_ID     = ${{nyanya-backups.ACCESS_KEY_ID}}
AWS_SECRET_ACCESS_KEY = ${{nyanya-backups.SECRET_ACCESS_KEY}}
AWS_DEFAULT_REGION    = ${{nyanya-backups.REGION}}
BACKUP_KEEP           = 30
BACKUP_PASSPHRASE     = <длинная случайная строка, отметить Sealed>
```

Имена в ссылках `${{…}}` — это имена сервиса и бакета в вашей панели; если бакет назван иначе,
подставьте своё.

**Код сервиса в репозитории пока не написан** — это отдельная задача, не выполненная в этом
пакете. Когда до неё дойдут руки, содержимое `nyanya-app/ops/db-backup/` должно быть таким:
образ `postgres:<та же мажорная версия, что у боевой базы>-alpine` плюс `aws-cli`, скрипт,
который делает `pg_dump --format=custom --compress=zstd --no-owner --no-privileges`,
шифрует результат (`openssl enc -aes-256-cbc -pbkdf2 -salt -pass env:BACKUP_PASSPHRASE`),
отказывается заливать подозрительно маленький файл, кладёт его в бакет и удаляет всё, что
старше `BACKUP_KEEP` последних копий (у бакетов Railway нет правил жизненного цикла, ротацию
делает сам скрипт). Версия `pg_dump` в образе не должна быть старше сервера: после мажорного
апгрейда базы поднимите тег, иначе дампы начнут падать.

**Про шифрование — решение владельца.** Плюс: утечка бакета не раскрывает ФИО, телефоны и
хеши паролей. Минус прямой и жёсткий: **потеряли пароль — потеряли все копии.** Пароль
хранится в менеджере паролей владельца и в переменной `BACKUP_PASSPHRASE` (Sealed). В
репозиторий его писать нельзя.

**Первый запуск** — вручную: сервис `db-backup` → Redeploy, в логах должна появиться строка
об успешном дампе. На следующее утро проверьте, что появился второй файл — от cron.

**Сколько стоит**: хранение 30 сжатых дампов по 10–20 МБ — около 0,5 ГБ, то есть ~$0,01 в
месяц. Загрузка в бакет считается исходящим трафиком сервиса: ~0,5 ГБ в месяц ≈ $0,03.
Сам запуск — несколько минут работы контейнера в сутки, доли цента. Точный размер дампа
станет известен только после первого запуска.

**Railway не оповещает о проваленном cron-запуске.** Поэтому либо раз в месяц смотрите, что в
бакете есть свежий файл, либо добавьте в конец скрипта пинг бесплатного сторожа
(healthchecks.io и подобные) — тогда о пропущенном дампе придёт письмо.

### 3.4. Копия вне Railway — раз в месяц, руками

Снимки, PITR и бакет лежат в одном аккаунте Railway. От блокировки или потери аккаунта
защищает только копия, которой там нет.

Раз в месяц (поставьте напоминание): скачайте один свежий дамп из бакета `nyanya-backups`
(вкладка Credentials у бакета даёт ключи для `aws s3 cp --endpoint-url …`) и положите его на
свой диск или в облако, к которому Railway отношения не имеет. Храните последние 3–6 копий.
Это бесплатно: у бакетов Railway исходящий трафик не тарифицируется.

Файл содержит персональные данные и хеши паролей — храните его там же, где храните паспорта,
а не в общей папке.

## 4. Учебное восстановление

Копия, которую ни разу не восстанавливали, — не копия. Прогон делается один раз сейчас и
повторяется раз в квартал; боевую базу он не трогает.

### 4.1. Из дампа (локально, в одноразовом контейнере)

```sh
# 1. скачать дамп (ключи — вкладка Credentials бакета nyanya-backups)
aws s3 cp s3://<BUCKET>/postgres/<файл> ./ --endpoint-url <ENDPOINT>

# 2. расшифровать, если дампы шифруются
BACKUP_PASSPHRASE='…' openssl enc -d -aes-256-cbc -pbkdf2 \
  -pass env:BACKUP_PASSPHRASE -in <файл>.enc -out db.dump

# 3. поднять чистый Postgres на 5435 — локальную базу разработки не трогаем
docker run --rm -d --name nyanya-restore -e POSTGRES_PASSWORD=drill -p 5435:5432 postgres:18-alpine
docker cp db.dump nyanya-restore:/tmp/db.dump
docker exec nyanya-restore createdb -U postgres nyanya
docker exec nyanya-restore pg_restore -U postgres -d nyanya --no-owner --no-privileges /tmp/db.dump

# 4. сверить счётчики с теми, что были на момент дампа
docker exec nyanya-restore psql -U postgres -d nyanya -Atc \
 'select (select count(*) from "user"), (select count(*) from specialist_profiles),
         (select count(*) from documents), (select count(*) from reviews),
```

## 5. Переезд в EU West (Амстердам)

**Зачем.** Единственный европейский регион Railway — `EU West Metal`, идентификатор
`europe-west4-drams3a`, Амстердам. У Railway нет точек входа в Центральной Азии, поэтому
трафик из Ташкента и так входит в их сеть в Европе; если сервисы стоят в Сингапуре, каждый
запрос делает лишний круг через два континента. Перед переездом посмотрите в панели, в каком
регионе лежит бакет с документами (проверить это отсюда было нечем): если он уже в Амстердаме,
после переезда приложение, база и файлы окажутся в одном городе; если нет — регион бакета не
меняется, и файлы так и останутся на другом континенте.

**Честно о выгоде**: обещать точную цифру нельзя. Замерьте сами из Ташкента до и после:

```sh
for i in 1 2 3 4 5; do
  curl -o /dev/null -s -w 'connect %{time_connect} ttfb %{time_starttransfer}\n' \
    https://www.nyanya.uz/catalog
done
```

**Юридически ничего не меняется**: данные и сейчас за границей, требование о хранении
персональных данных в Узбекистане остаётся невыполненным (см. `docs/TODO.md`) — переезд из
Сингапура в Нидерланды его не закрывает и не ухудшает.

**Цена**: регионы стоят одинаково. Домен, DNS, приватная сеть и `DATABASE_URL` не меняются.

### Окно

Простой будет — при переносе тома базы. Railway честно пишет, что время зависит от размера
тома и не гарантируется: при базе в сотни мегабайт ждите 5–15 минут, но может быть и дольше.
Выберите ночь по Ташкенту (например, воскресенье 03:00 = 22:00 UTC субботы) и согласуйте её
заранее. Страницы, которым нужна база, в это время отдают ошибку: **страницы «технические
работы» в приложении нет** — это отдельная задача, не сделанная.

### Порядок

**0. За час до окна.**

- снимок счётчиков (§0);
- `railway postgres pitr backup create --service Postgres --name pre-region-move`, дождаться
  завершения, `backup lock <ID>`;
- ручной запуск `db-backup` (Redeploy) и свежий файл в бакете;
- монитор (§2) — поставить на паузу или предупредить себя, что оповещение придёт;
- записать текущий `DATABASE_PUBLIC_URL` из переменных Postgres.

**1. Сначала приложение.** Сервис `nyanya` → Settings → Deploy → Region → `EU West Metal`.
Тома у приложения нет, поэтому простоя не будет: Railway пересоберёт сервис и переключит
трафик, и проверка живости (§1) не даст переключиться на сломанный контейнер. Займёт 5–8
минут. В это время страницы будут медленнее — база ещё в Сингапуре, это ожидаемо и коротко.

Почему приложение первым: сборка (`npm install` до 7 минут) не должна лежать на критическом
пути простоя базы.

**2. Сразу база.** Сервис `Postgres` → Settings → Region → `EU West Metal` → Railway покажет
окно про перенос тома → подтвердить. Сервис останавливается, том копируется, сервис стартует.
Это и есть простой.

**3. После старта.**

- `railway postgres pitr status --service Postgres` — архиватор здоров (если PITR включён);
- счётчики совпали с теми, что сняли до окна;
- `https://www.nyanya.uz/api/health` → 200, `/`, `/catalog`, `/verification`, `/login` → 200,
  одна анкета по прямой ссылке → 200, фотография на ней открывается (бакет не трогали);
- вход владельца в `/admin` работает;
- переменные Postgres: если `DATABASE_PUBLIC_URL` изменился (прокси может быть пересоздан) —
  обновите его там, где он у вас записан; локальные служебные скрипты берут адрес оттуда.

**Если перенос тома завис или упал**: обращение в поддержку Railway, а запасной путь — новый
сервис Postgres в EU из того же образа, `pg_restore` свежего дампа в него, переключение
`DATABASE_URL` сервиса `nyanya` на новый сервис, старый удалить не раньше чем через неделю.
На новом сервисе заново включаются расписания снимков и PITR.

**Откат**: регион переключается обратно тем же переключателем (приложение — без простоя, база —
снова с переносом тома). Если после переноса данные окажутся неполными — восстановить снимок
`pre-region-move` (Backups → Restore → Deploy).

## 6. Сертификат боевой базы: что сейчас есть и чего нет

Служебные скрипты (`scripts/delete-accounts.mjs`, `set-password.mjs`, `set-gender.mjs`,
`purge-orphan-files.mjs`) ходят в боевую базу через публичный прокси с `ssl: "require"`.

**Честно: `require` шифрует соединение, но сертификат сервера не проверяет.** В драйвере
`postgres` 3.4.9 значения `require`, `allow` и `prefer` выставляют `rejectUnauthorized = false`
(`node_modules/postgres/src/connection.js`). То есть трафик нельзя прочитать со стороны, но
узел на пути в принципе может представиться боевой базой — а через эти скрипты идут удаление
аккаунтов и смена паролей.

**Что нужно для настоящей проверки (verify-ca)** — и почему это шаг владельца: образ Railway
`postgres-ssl` при первом старте сам выпускает корневой сертификат (`CN=root-ca`) и подписывает
им серверный. Оба лежат на томе базы, забрать их может только тот, у кого есть доступ к
аккаунту и зарегистрированный SSH-ключ:

```sh
railway ssh keys add --key ~/.ssh/id_ed25519.pub --name "ноутбук владельца"
railway link                                   # проект nyanya.uz, окружение production, сервис Postgres
railway volume files list /                    # найти каталог с сертификатами (ожидаемо certs/)
railway volume files download /certs/root.crt ./railway-postgres-root.crt
openssl x509 -in ./railway-postgres-root.crt -noout -subject -enddate      # subject=CN=root-ca
```

Проверить, что этим сертификатом действительно подтверждается боевая база (host:port — из
`DATABASE_PUBLIC_URL`):

```sh
openssl s_client -starttls postgres -connect <host>:<port> \
  -CAfile ./railway-postgres-root.crt </dev/null 2>/dev/null | grep 'Verify return code'
# ожидаемо: 0 (ok)
```

Корневой сертификат — не секрет, его можно положить в репозиторий. **Но код проверку пока не
делает**: чтобы её включить, нужно передать драйверу `ssl: { ca, rejectUnauthorized: true }`
и отключить проверку имени хоста (серверный сертификат выписан на `localhost`, а не на адрес
прокси). Это отдельная задача — она начинается с того, что владелец скачает файл выше.

Сертификат меняется примерно раз в два года, а также после восстановления базы в новый сервис
и после мажорного апгрейда Postgres. Когда проверку включат, скрипты в такой момент честно
откажутся подключаться — файл надо будет скачать заново тем же способом.

**Альтернатива без публичного прокси**: `railway ssh --service nyanya -- node scripts/set-gender.mjs …`
— скрипты и зависимости есть в контейнере приложения, соединение идёт по приватной сети.
Для `delete-accounts.mjs` неудобно: JSON-дамп останется внутри эфемерного контейнера.

## 7. `railway.json` → `.railway/railway.ts`, срок — до 1 декабря 2026

Config as Code (`railway.json`) объявлен устаревшим. Документация Railway: существующие файлы
читаются для уже настроенных сервисов **до 2026-12-01** (жёсткая отсечка), новые сервисы
подключить к этому механизму уже нельзя. После отсечки действуют только значения из панели и
Infrastructure as Code. Если ничего не сделать и не продублировать настройки в панели (§1),
в этот день тихо пропадут и проверка живости, и предзапуск миграций — деплой поедет без
`npm run db:migrate`.

**Делать не позже середины ноября 2026**, спокойным днём, вручную и интерактивно:

```sh
cd nyanya-app
npm install --save-dev railway            # SDK, которым CLI читает .railway/railway.ts
railway link                              # проект nyanya.uz, окружение production, сервис nyanya

railway config migrate                    # предпросмотр: railway.json → .railway/railway.ts
railway config migrate --apply --delete-files   # записать файл, снять «Config File» с сервиса, удалить railway.json

railway config plan                       # ЧИТАТЬ ГЛАЗАМИ
railway config apply                      # только если в плане «0 to destroy»
```

Ожидаемый файл для одного сервиса (миграция одного сервиса пишет именованный partial — это
хорошо: правило «чего нет в файле, то удаляется» действует только на ресурсы этого файла,
Postgres и бакеты он не тронет):

```ts
import { defineRailway, project, service } from "railway/iac";

export const partial = "nyanya";

export default defineRailway(() =>
  project("nyanya.uz", {
    resources: [
      service("nyanya", {
        start: "npm run start",
        preDeploy: "npm run db:migrate",
        healthcheck: "/api/health",
        healthcheckTimeout: 120,
      }),
    ],
  }),
);
```

**Правила безопасности этого шага:**

- **«omit = delete».** Файл, в котором нет Postgres и бакетов, при полном владении проектом
  запланирует их удаление. Поэтому: читать план целиком, соглашаться только на «0 to destroy»,
  никогда не запускать `railway config apply --yes --confirm-destructive`.
- Не делать `railway config pull` всего проекта, если не готовы разбирать весь получившийся файл.
- Адрес и таймаут проверки живости в справочнике IaC есть (`healthcheck`,
  `healthcheckTimeout`), а политики перезапуска и расписания cron там не описано — считайте,
  что они остаются в панели, и после каждого `apply` проверяйте, что Restart Policy у
  `nyanya` и Cron Schedule у `db-backup` на месте.
- После `apply` сделайте один пробный деплой и убедитесь, что миграции в pre-deploy отработали
  и healthcheck прошёл.
- Возвращать `railway.json` из истории git смысла нет: после `migrate --apply` Railway его
  больше не читает.

превышении Railway приостановит доступ к бакету и сервисам, поэтому лимит должен быть с
